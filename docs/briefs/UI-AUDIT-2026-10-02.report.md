## Five prioritized findings

1. **P0: finish the design-to-game handoff before extending the editor.** T078/T079's controls, presets, state skins and responsive tools do not reach gameplay. A design approved in Studio cannot currently be applied in Game Builder or the player. Studio History says it will appear when connected to the engine (13); preview saves record only screen/line position. This is the largest explanation for apparent lack of UI progress.
2. **P1: the live mobile navigation is clipped and overlaps the clock.** At 390x844 the right rail labels sit partly outside the viewport (05/06). Runtime CSS deliberately uses a negative right offset and hover expansion; this is a poor touch route. Desktop History measured x=1330, width=118 in a 1440 viewport. Studio already supplies independently positioned controls and device anchors (15); exporting those does not fix the game until it resolves them against the real stage. Dialogue/input remain readable in the captured phone scene, so preserve them.
3. **P1: shipped feedback is not visually placed beside the response.** The live player DOM contained Jana's mood row; #scene-feedback measured x=0,y=16,width=1440,height=18 while the stage screenshot showed no visible mood row (03/04). play.mjs inserts it before the absolutely positioned composer; the linked play styles contain no scene-feedback rules. This is a placement/style integration gap, not a missing judge. Add a visible bound feedback region to the skin; preserve the decided chips/mood options and hidden-stat policy.
4. **P1: Studio preview content cannot establish runtime fidelity.** The mock uses sample date/balance/Brain-Heart-Body values, two project choices and an illustrated backdrop (11/12); real Ashford has its own cast, clocks, many actions, costs, gates, planner and scene/end/day cards (02-07). Studio long-text works (16), and error appears in the choice/response panel (18), but selecting Response failed on Dialogue still shows normal dialogue without a response-error control (17). Test state coverage on the actual target screens. Never bind sample stats or relationship numbers merely because a widget exists. The 290px Phone canvas and fit-content resizing are useful authoring aids, not full-window accessibility QA.
5. **P2: creator/navigation hierarchy remains separate from interface design.** The real Builder has 53 equal-level project sections and 6,980 form controls in the copied Ashford DOM; initial expanded sections produce a 337,290px document at desktop (08/09). Navigation and labels exist, but locating appearance versus narrative rules is hard, and no Studio skin assignment is offered. At phone size the document's layout width grew to 470px for a 390px target (10). The player launch list also exposes 19 packs, including fixtures/duplicates (01). A clear Play / Create world / Design interface handoff would reduce confusion without moving creator/debug forms into the scene.

The current warm identity, bundled font options, distinct dialogue frame and persistent composer are strengths (03). Planner reward hints are primarily title attributes rather than visible/focus-accessible explanations (04). Improve spacing and hierarchy around known costs, the next action and learned hints; do not make generic claims that serif, dark surfaces, animation or hover are absent/bad. Venus's written reference supports one focus NPC, short beats, automatic staging, a primary input and visible consequences. Existing owner decisions already retain visible hearts and instant ADV; do not reopen those mechanically.

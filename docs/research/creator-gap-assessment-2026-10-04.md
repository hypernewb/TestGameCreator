# Reusable social/romance creator: capability assessment

T-098, owner-authorized 2026-10-04. Assessment and documentation only; no implementation dispatch or integration approval. [Brief](../briefs/T-098.md), [report](../briefs/T-098.report.md), [current roadmap](../NEXT-MILESTONES.md#creator-milestones-2026-10-04).

## Decision and scope

Build a reusable creator/editor capable of authoring essentially the whole **kind of social/romance experience Venus University offers**: characters, world rules, encounters, authored events, progression, memory and player-facing screens. Functional authoring capability is the goal; polish alone is insufficient. The assessment finds a substantial reusable engine and working creator pieces, but **does not establish a complete no-code creator**. The main constraints are incomplete visual rule coverage, unreliable preservation of unsaved work, disconnected workflow evidence, and unverified delivery of reusable Game UI selections to live play.

The first usable milestone is a social/romance creator. Offer a ready-made social/romance template **by default** and a blank project as an explicit alternative. Existing prompt or SillyTavern-card startup remains an entry point for editable **1–8 NPCs (player excluded)** and **1–8 locations**. Creators own stages, unlocks, boundaries and authored events. AI improvises within those rules and proposes gameplay consequences only through engine validation. Core systems require visual controls; code may extend the product but cannot be a prerequisite for completing a core authoring task.

Memory requires automatic capture and inspect/correct controls, with optional author-defined facts, secrets, knowledge ownership and promises. A tiny sample proves author/play/debug/revise/save/reopen without code edits; it is not a full game design. Creator UI is the editor; Game UI is player presentation; UI Wizard edits reusable Game UI. Neither Game UI visual redesign nor editor chrome redesign is authorized. Installer, full mechanics migration and calendar-picked-date scheduling stay deferred. Weekly rules take priority, with explicit/specific rules overriding general rules. Adventure is LATER: engine-resolved narrative combat first, structured turn-based combat later. The eventual isekai fantasy setting may test social portability; party/adventure mechanics are not current gates.

## Evidence interpretation and priority rationale

**Preservation comes before adding authoring power.** The browser audit shows creators can lose edits during an apparently successful Save and can lose an entire unsaved startup review on refresh. Adding more fields or a larger template increases the amount at risk. Candidate ownership guards may solve part of this; independently review them first to avoid duplicating an overlapping patch. Warn/recover policy and raw-buffer handling remain distinct follow-ups. An engine backup is useful after a commit and does not solve this editor problem.

**Template entry comes before broad form expansion.** A template makes “core” concrete, gives defaults that work together and exposes the complete loop with little content. Blank mode prevents forcing every creator into those rules. Prompt/card startup already has bounded generation/review, so the useful addition is composition with the chosen base project, not replacing generation. The trade-off is a deliberately limited first template; record unsupported optional fields visibly instead of promising every historical module on day one.

**Expose existing rules before building more mechanics.** Relationship transitions/rank gates, plan-state conditions, event payload constraints and ending requirements already have engine support. Visual adapters and preservation/validation can unlock more creator capability at lower integration risk than another parallel rules engine. Reuse the existing conditions/effects schema and debugger. Core coverage must eventually include enabled social systems such as boundaries, daily caps and knowledge, not just the fields the tiny demo happens to use.

**Memory needs a connected correction contract, not an automatic vector-database project.** Current memory, scoped lore, generated facts, plans and relationship secrets have different stores/semantics. Unifying inspection and correction can use those sources; adding a second “secret memory” store risks competing truth. First specify provenance, visibility, precedence and a bounded reject/correct/reassert fixture. Retrieval sophistication or semantic quality should follow observed failure, not unverified papers.

**Functional player presentation is a creator capability, while appearance work stays paused.** UI Wizard import/storage is already delivered, but selection alone does not produce live screens. Functional binding has to respect the existing selection contract and generic world shapes when separately authorized. Accessibility/input visibility, cost/outcome feedback and save/recovery can be assessed without redesigning appearance. Finished artwork, audio automation and installer work cannot compensate for rules that are uneditable or edits that vanish.

**Fun and believability remain a separate evidence axis.** Deterministic tests can prove a promise is kept, the right person knows it, a stage unlocks and replay agrees. They cannot prove the promise matters emotionally, the character sounds alive or the time trade-off is interesting. No invented success percentage or old campus proxy decides creator completion. Later approved provider/human runs should use recorded inputs and mechanical traces and report specific examples of repetitive, contradictory or useful output. No paid/real-model evaluation is authorized now.
